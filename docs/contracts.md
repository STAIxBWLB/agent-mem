# Memory profile contracts

The default remains the shared `agent-hub.memory/v1` profile. The schema string, content hashes, segment format and reducers stay unchanged. `src/memory/ops-contract.ts` declares the current operation vocabulary and the reserved truth-changing operations. `MemoryStore.appendBody` and the separate `importNote` append path refuse unknown or truth-changing operations before appending bytes. This is a writer boundary, not validation of externally edited segments. Older/raw writers remain outside this version's mutation lock.

Truth-changing operations require a person-run generation migration and their own payload/reducer contracts. No reader inventory, announcement or successful compatibility check permits them in shared-v1 segments. The generation profile enables exact-entry `prune` and local exact-entry `vault_link`; `correct`, `lift`, `consolidate` and `group` remain blocked. `OP_CONTRACTS`, `V1_OPS` and `assertSharedV1Op` retain their shared-v1 meaning. The separate `GENERATION_OP_CONTRACTS` declares the enabled generation contracts and names `validatePruneRow` and `validateVaultLinkRow` as their runtime validators. Metadata alone never grants writer authority.

For shared v1, C05 remains a declared ceiling: expiry removes derived rows using the wall clock without a durable prune operation. Moving the clock backward can leave the incremental index empty while a rebuild restores the authored row and its edges. The clock-rollback fixture asserts this exact divergence, unchanged authored bytes and stable subsequent rebuilds. It does not claim universal incremental/rebuild equality across backward time. C02 has a generation counterpart: a live generation handle hashes only appended bytes but still reads and compares the whole prefix of a changed segment to catch rewrite-plus-growth, so a changed refresh costs O(segment) I/O (about 13 MB and 247 ms p50 at 20,000 entries in the [read receipt](bench/p9-generation-read.md)). Unchanged segments cost no data I/O. The upgrade, measured first, is a per-block hash chain or a tail window plus an inode/size check.

## Generation-only prune

The generation layout, selector, one-way bridge and coordinated rollout are bound by [agent-mem issue #9](https://github.com/STAIxBWLB/agent-mem/issues/9), revision 2. Existing v1-equal authored rows keep their schema and IDs. All writes by a generation-bound handle stay under `M/generations/G/`, with a separate Git repository and `refs/heads/amem/gen/G`. Legacy directories, index, machine identity and `main` remain untouched. A handle stays bound until closed; a selector change does not reopen running hub stores.

Prune rows use `agent-mem.prune/v1`, actor `person`, a generation ID, canonical authoring time/cutoff, machine, local/synced placement and sorted full-ID targets. Each target carries the full SHA-256 of its canonical authored row including id, expiry and exact basis row/hash. The prune row's own id is the first 32 hex of SHA-256 over the complete canonical payload excluding id. `validatePruneRow` rejects extra/missing nested fields, invalid IDs/hashes/times, unsorted/duplicate targets, more than 32 targets or a row over 16 KiB UTF-8.

Only serialized deadlines qualify: a note must carry its own canonical `expires`, or its demote/settle basis must carry canonical `by`. An implicit `at + 180 days` backstop or an instance TTL fallback is ineligible. A person can first author an ordinary v1 demote/settle with an explicit deadline. The person-authoring boundary checks effective observed expiry against its full captured state; a replica verifies target/basis identity and the explicit witnessed deadline. It cannot prove the author knew every later/offline deadline, and no private/global frontier is published to claim that completeness.

`exact-entry-v1` masks only the listed full target IDs. A same-ID replay remains gone across clock rollback and later deadlines. Another ID is independent even when text matches or it is a later promotion of that entry. Missing promotion ancestry alone never quarantines ordinary synced notes. Retained raw promotion metadata still hides a short-term source when its promoted copy is tombstoned. A pruned replacement remains permanently gone when evaluating supersession, so rolling the clock backward cannot hide its predecessor again. Get/alias/graph-start resolution must not bypass the exact mask. Raw debug logs/dumps retain authored rows and are not evidence-only projections.

A prune received before its target or expiry witness is pending, not evidence. Wrong generation, placement, row hash or impossible expiry proof is quarantined/refused. Read-only projection calls never author prune. Generation raw rows are retained rather than deleted at wall-clock expiry, allowing full derived-table equality on rebuild; unpruned views may still change under clock rollback.

## Generation-only vault links

`vault_link` uses `agent-mem.vault-link/v1`. Its complete canonical payload carries a full exact note ID, SHA-256 of the complete authored note including ID, project, relative Markdown path, generation, authoring time, machine, person actor and local placement. Its own ID is the first 32 hex characters of the complete canonical payload hash excluding ID. The validator refuses extra or missing fields, changed hashes, noncanonical times, unsafe paths, foreign generations and public placement. The maximum payload is 4096 UTF-8 bytes; the path is bounded to 512 UTF-8 bytes.

Only the witnessed exact entry stops appearing in vault candidates. A different immutable entry remains independent. Missing or mismatched target witnesses cannot suppress a candidate. The curated note remains available as ordinary evidence, and raw authored rows are retained. The path is metadata: amem never opens, writes, indexes or copies a vault. There is no MCP link-write tool.

Current standalone policy and the stricter host policy screen candidates before selection, ordering, limits and counts. Link authoring rechecks the exact target ID/hash under the mutation fence, appends and fsyncs a complete local row, then refreshes the derived index. It refuses an incomplete prior tail. Complete rows replay and rebuild; a partial tail requires person inspection. Link rows remain local during sync and follow the target's owner through curated shard migration. The frozen writer fixture proves the ordinary evidence remains readable while candidate suppression survives rebuild; `test/vault.test.ts` covers policy, exact target boundaries and shard migration.

Published 0.3.1 is the exact-pinned pre-vault reader used by the compatibility fixture. Ordinary listing can keep working through the shared derived index already advanced by a P2 writer; a full rebuild rejects the unknown operation. An independent unadvanced index also refuses when refresh must parse that suffix. The fixture deliberately excludes the derived index to force that rebuild on open. Published 0.1.1 and 0.2.0 only establish shared-v1 isolation because they predate generation support; they cannot prove unsupported-generation refusal. These are synthetic compatibility receipts, not verification of installed readers or a live rollout.

Do not record vault links on a memory home used by a 0.3.1 host, including agent-hub while its exact pin remains `@staix/agent-mem` 0.3.1. Upgrade the sharing host to a pin that includes P2 vault-link support before authoring the first link. A successful ordinary list through the older host is insufficient: its next rebuild will refuse that generation. This guard does not authorize installation, a restart or a real-home mutation.

## Plans, privacy and recovery

The local plan envelope is `agent-mem.prune-plan/v1`, with generation, selector revision, host-bound project and policy revision, ordered `{placement,payload}` rows, counts, `hasMore` and a SHA-256 seal over its canonical bytes excluding seal. The selector revision is a canonical selector hash or `absent`. Limits are 256 KiB before parsing, 16 rows and 256 total targets, plus per-row limits. Automatic planning chooses a deterministic full-ID prefix and reports `hasMore`; explicit oversized target requests refuse. The seal detects changes, but grants no authorization. Apply rechecks person intent and bound generation/machine/selector/project/policy; every not-yet-durable row must also pass exact target/basis hash and current observed-expiry checks before journal/append. Completed immutable row IDs are resumed as durable receipts rather than reauthorizing their tombstones against a later deadline.

Standalone amem authors local masks only, including masks over synced notes. `--policy-free` cannot authorize a synced prune. The host's public policy must attest the exact normalized row hash, generation, project and current policy revision; target and basis must already be public generation rows or verified cached legacy-main witnesses. Unpublished legacy-root logs, local/private bases and private/unknown classifications remain local. No private IDs, closure hashes, private counts or local aggregate seals enter synced rows, errors or public receipts. Detailed plan counts and receipts are person-local. A policy refusal/change invalidates the plan; no silent repartition occurs during apply.

Apply persists and fsyncs the exact local plan before authoritative rows. Under the generation mutation fence it appends complete rows and fsyncs before refreshing the index. Atomicity is per row; local/public partitions are not one transaction. Resume skips durable IDs and completes a partial own tail only when its existing bytes exactly prefix the same persisted planned line. Mismatched tails refuse; complete log lines are never truncated or rewritten. An index failure is recoverable from durable rows.

Migration activation uses the home-wide PID/signature `profile.lock`, captured source-prefix receipts, staged rebuild validation and fsynced metadata; selector replacement is the last commit point. Resume keeps the same G. Corrupt/missing active state blocks rather than silently falling back to shared v1. Deactivation retains both histories and intentionally omits generation-only notes/prunes from the selected v1 view. It is not a lossless rollback.

Explicit deactivation validates the selector but does not require a valid generation descriptor, seal or directory. It switches back under the profile lock and retains all data; a healthy existing generation mutation fence is respected. Normal selection keeps failing closed on corrupt active state. Crash fixtures interrupt after seal, before and after selector replacement, and reopen after the first generation append.

Malformed complete legacy lines are skipped and counted in both migration modes and person-local status. Unknown operations and content-ID mismatches are malformed legacy input; they do not block later valid rows. Generation-authored segments retain strict validation. Prefix rewrites/truncation and non-fast-forward legacy input remain fatal. `MemoryStore.bridgeStatus()` returns only the skipped count, and standalone human CLI output includes it; model-facing raw-command callers do not receive the optional status callback by default. JSON note arrays are unchanged. Generation settlements and promotions affect generation-born identities only; a bridged identity keeps legacy birth even if its same immutable ID is replayed into a generation segment.

A settlement row witnessed in both legacy and generation input retains both source-presence bits, so replay order cannot move a deadline from one projection to the other. Legacy birth wins conservatively for duplicate note identities. Generation segment counts include the bridge's consumed inputs, so a rebuild receipt cannot report zero segments for a nonempty bridged home.

Shared-v1 sync uses its unchanged direct Git spawn and caller Git configuration environment. Only generation sync uses the separate environment-isolated, child-umask invocation. The prune CLI opens its plan once without following a symlink, validates that descriptor with `fstat`, reads at most 256 KiB plus one overflow byte, and refuses growth, truncation or invalid UTF-8 before store access.

## Rollout and unverified legs

This source implementation neither migrates real memory nor proves deployment. Before real migration, a separate agent-hub task must exact-pin the released generation-capable package and bind store consumers, sync, sidecars and host policy to the same profile. The person's installed amem and running hub must prove matching canonical home/G/selector revision and loaded package through a synthetic cross-write/read/prune preflight. Quiesce and close known local handles before separately approved real migration, then reopen and verify running bindings before resuming writes. Old/unsupported or differently configured consumers must refuse visibly; on-disk package metadata alone is not running-store proof.

Candidate/counter sidecars are not migrated or synchronized. The standalone `amem review` CLI accepts general memory candidates through the selected generation or project shard with current standalone policy. Older correction/failure candidate paths retain their profile-aware integration guard. Host rollout, installed-session preservation, real-home migration, real multi-machine sync and host recall/brief/ask/capture/PII-turn receipts remain open live gates. Synthetic fixtures do not close them.

Complete parsed prune bytes are not a durability receipt. Apply always crosses the append hook's fsync fence, even on an idempotent resume. A private per-segment pending claim binds plan seal, row ID, expected byte offset, prefix hash and planned line hash before append. Only that plan can complete a partial tail; ordinary generation writes and public sync refuse an outstanding relevant claim. Files and containing directories are fsynced before completion. Local metadata writers enforce the same 256 KiB byte limit as their readers before opening a temporary file.

Explicit legacy fetch/sync verifies Git history and captures immutable legacy-main blobs plus an atomic plain-file manifest. Normal bridge reads use that captured input and never spawn Git. Segment checkpoints retain size/inode/nanosecond time metadata alongside their verified prefix hash. Unchanged input, including a reopened handle, reads and hashes no segment bytes. A seeded live handle uses SHA state copies to hash appended suffixes only; on a changed file it still reads and compares the old prefix, so prefix rewrite plus growth remains fatal. This does not claim suffix-only disk I/O. A cold handle that first finds a changed segment verifies/seeds the complete prefix once; an explicit rebuild verifies full input. The cold O(segment) path is a declared ceiling, with serialized hash state or per-block receipts deferred until measurements warrant them.

Only newly completed suffixes are parsed/applied. Initial migration receipts verify input but never substitute for consumed rows in a recreated derived index. A captured-input transaction verifies its checkpoint frontier before commit and retries boundedly if another handle advanced it; it never rolls the shared watermark backward. Prune targets and row projections are read from the same WAL snapshot. The synthetic read receipt separates warm unchanged, unchanged reopen, seeded live append and cold changed cases; it does not establish a before/after speedup or live-home latency target.

## MCP candidate reads (#13, task #209)

`amem_search`, `amem_timeline` and `amem_show` do not refuse because a tier exceeds 5,000 rows. They read at most 256 candidate bodies per SQL keyset page. Exact startup-bound project identity, `since`, chronological/anchor ordering and the query predicate run inside the derived query. Curated relations still fold over complete lifecycle metadata so forgetting, supersession, promotion, expiry and generation masks retain their existing semantics; only candidate bodies are materialized. Cold curated FTS reconstruction streams bodies into the existing derived cache.

Search ranks the newest 5,000 permitted matching candidates per tier. Raw FTS is a match predicate, never a BM25 preselection: each complete row passes current standalone and host policy before it consumes that public candidate window. Denied or invisible rows cannot exhaust the public window. BM25 and tier/recency weights are computed in a temporary FTS index containing only screened candidates. This is a bounded recent matching window, not a claim of globally best ranking over an arbitrarily large history. `since` can narrow the window; a policy-bound persistent ranking index is a future upgrade. Without FTS, or when lazy capture indexing is absent or contended, paged substring matching retains the explicit fallback engine. The first capture page chooses and pins that engine for the entire search, including an empty page. Both tiers apply complete-row policy and true substring matching before candidate caps; no curated FTS predicate or temporary FTS ranking runs during fallback. A later independent read retries lazy initialization after contention clears.

Capture's independent derived `mcp_fts` indexes the same body MCP searched before this change: excerpt, decoded paths and event. It uses the same tokenizer as public ranking, including Korean particle variants, Unicode case and diacritics. The existing library excerpt-only `fts` remains separate. Capture hooks and append never create or backfill `mcp_fts`. Only a queried MCP read lazily creates its table, triggers and historical SQL backfill in one immediate transaction. That snapshot covers all pre-initialization appends; after commit, triggers keep it level across append, replay, update and eviction. Timeline, show and capture-disabled search never initialize it. The MCP read accepts this one-time indexing cost; R2 hook admission does not. Neither changes authoritative capture rows or curated schemas, hashes, segments or paths.

Timeline resolves and screens an anchor directly, even outside a recent search window, then pages nearest or latest rows until each tier has enough permitted entries. `since` restricts the neighborhood, not anchor lookup. Point/prefix reads use the same lifecycle and policy checks; ambiguous permitted prefixes return no row. No foreign shared-project note is admitted. The graph complete-history ceiling is separate and unchanged; work-list replay is described below.

The actual stdio resource script seeds 5,001 curated and 5,001 capture rows, plus 10,001 work-list appends reduced to 100 items. It checks search, capture-disabled and capture-only queries, time filters, latest and anchored timelines, work reads, R3 idle/peak RSS and EOF process reaping on both CI platforms. Synthetic homes are used; this is not a live cutover or a new release.


### Reviewed alias and curated rows (#27)

`aliases.jsonl` holds two op kinds: `alias` (`alias`, `key`) and `unalias` (`alias`). The latest op per alias key wins and nothing is rewritten, so an older reader that only knows `alias` ignores the removal line and shows its older view. `amem alias remove` refuses a key that is not aliased now.

For an aliased key the CLI and MCP exact-project filter widens to the canonical key plus every key aliased to it, for notes, goals, suggestions, search, timeline, show, vault candidates and links, candidates and counters, and work lists. Rows keep their own project in the log and read as the canonical key. The widening is opt-in through `StoreOptions.reconcile`, `CandidateStore({ reconcile })` and `WorkListStore({ aliases })`: the library default and `amem prune` keep the exact key, so a prune plan never names rows of a key it was not asked about. Under curated shards the aliased key's shard is opened read-and-own beside the canonical one (never created when absent), and a settle, forget, supersede or promote of an aliased row is appended to the shard that holds it. The MCP guard closes the session when the effective alias set changes.

Every write that copies a row keeps the key the row was written under, never the canonical label a reconciled read shows: a promote's long-term copy and a vault link name the raw project, so a raw-key reader, a non-reconciled host and the same note promoted on another machine all produce the same row and id. Known limits: (1) `aliases.jsonl` is not synced and an amem or hub older than this change ignores the `unalias` line, so it keeps binding the old key to the canonical one for capture, work lists and the MCP binding until it is upgraded; upgrade every host that shares the home before relying on `alias remove`. (2) A correction accepted on an aliased row is a new note under the canonical key, and its supersede op is appended to the shard that holds the old row. After `alias remove` the old key's shard shows the old note again, because the replacement lives in the canonical shard. This affects visibility only, nothing is lost, and the replacement stays readable under the canonical key.

### Hook upgrade regression (#13, task #327)

`test/capture-mcp-lazy.test.ts` seeds 5,001 maximum-length capture excerpts, removes only the derived MCP index to represent a pre-upgrade shard, and opens/appends through the ordinary hook store. Transparent SQL-call recording observes the real row insert and zero MCP-index statements on that hook path; the unchanged SQLite schema version and absent MCP table/triggers independently verify its effects without a load-sensitive timing assertion. A lazy read then includes both historical and pre-initialization appends; later inserts, updates and deletes retain index parity. A first open under a real SQLite writer lock returns bounded substring pages, and the same handle retries after release. ## Concurrent capture spool publication (#13 P3 prerequisite)

Contended capture appends publish one private, complete immutable segment per event in the shard's `spool/` directory. A unique process/sequence/random name is first written and closed in `spool/.writing/`, then atomically renamed into the readable directory. No writer appends to an inode a drainer can read. Each drain claims a segment by atomic rename to a unique `.draining-<nonce>` name. A recovery drainer may reclaim even a live claim; replay hashes each complete screened line into the existing unique `spool_id`, so competing readers and a crash after commit remain idempotent. A drainer only removes or renames its exact claim, never a fixed name another drainer can replace.

Large legacy files keep their immutable bytes. After the SQLite transaction commits, a rename acknowledges the consumed byte offset in the filename; a crash before that rename replays the prefix safely. Each invocation inspects at most 256 directory entries, claims at most 32 files, reads at most 256 KiB and inserts at most 1,000 lines, with a 25 ms admission deadline between files. This is a work bound, not preemption of an active filesystem or SQLite call. Complete newline-delimited rows cross byte windows without splitting UTF-8. A short leftover allowance defers the next incomplete row at the same byte offset; only a full 256 KiB window can mark a line oversized. An oversized malformed line is discarded through its next newline, counted once, and cannot hide a later valid line. Fixed `spool.jsonl` and `spool.jsonl.draining` inputs remain readable for upgrade; new appends never create them.

An upgrade must quiesce old capture writers: a newer reader cannot repair an inode still opened by an old shared-spool writer. A process killed before publication can leave an unpublished `.writing/` file; it is deliberately never replayed because its last row may be incomplete. Removing such files is quiescent maintenance. Power-loss durability of an interrupted append is not claimed; an fsynced journal would be a separate upgrade. Capture rows, screening, lazy MCP FTS, curated log schemas, hashes and segment paths are unchanged. Deterministic subprocess filesystem barriers prove both the stale-drainer deletion and already-open writer races; two concurrent identical writers with two drainers also retain both events exactly once.


## Complete work-list replay (#13, task #210)

Work-list reads have no persisted-operation count ceiling. The derived index stores a replay key for each row and streams its ordered cursor, keeping only the latest permitted scalar values per list/item field. Timestamp, import-origin, numeric source-id, same-machine append position and hash tie-breaking retain their earlier order, including JavaScript UTF-16 lexical order. Null clears a field. Current policy runs on every row before reduction and closed-list filtering; a failed policy never changes visible fields or state.

Each read pins a separate read-only SQLite snapshot before the mutation lock is released. A host policy may await while another writer appends; the initial read keeps its original frontier and a later read observes the append. Iterators and snapshots close on completion or error. The additive replay column is derived only: older derived indexes are upgraded, and rows indexed by an older writer are backfilled one at a time. Append-log bytes, hashes and public API signatures are unchanged; incremental and full rebuild results remain equal.

Memory is bounded by the current result's distinct lists/items/fields and a small SQLite reader cache, not an array of historical payloads. Reads still verify log bytes and examine the complete applicable history, so time grows with history; an enormous current result also needs its result memory. Paged materialized views are a future upgrade if measured usage requires them. The real stdio MCP budget fixture now includes 10,001 work operations and checks every item's latest progress with the existing idle <100 MB, peak <200 MB and EOF-reaping assertions.

- A writable `CaptureStore`, `sessionStartBrief` and `createMemoryMcp` refuse a project that is not active (the brief returns the unavailable result, MCP throws its generic unavailable error), and their binding guards re-check the state, so an op recorded mid-session takes effect at the next call. `CaptureStore({ lifecycle: "ignore" })` is for gc and export only and never appends.
- `runGc` opens only capture stores. Nothing in it reads or writes `log/`, `local/`, `work/` or an index of the curated tier (`test/usage-gc.test.ts` holds the shard's non-capture files byte-identical across a run).
- Cross-project reads are person commands. `searchAllProjects` and `vaultCandidatesAll` open one project's curated store at a time through `openCuratedForRead`, which never initializes a store, and write nothing under the home. Their replies carry `crossedProjects` and the projects read. MCP has no all-projects argument.
- `exportProject` claims its destination with `O_EXCL | O_NOFOLLOW` (the existence check only gives the message), refuses a destination inside the memory home and a forgotten project, screens every value with the secret screen and the caller's policy, and removes only the partial file it created on failure.
- The R7 split (`capacitySplit`) takes only capture quantities (bytes in use, bytes per day, last capture time). Its caps are whole MB, sum to at most the budget, are at least 1 MB, and never fall below a shard's current use unless the budget forces it (the row says so). `capacity apply --split` writes each non-forgotten shard's `config.json` and nothing else.
