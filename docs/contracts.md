# Memory profile contracts

The default remains the shared `agent-hub.memory/v1` profile. The schema string, content hashes, segment format and reducers stay unchanged. `src/memory/ops-contract.ts` declares the current operation vocabulary and the reserved truth-changing operations. `MemoryStore.appendBody` and the separate `importNote` append path refuse unknown or truth-changing operations before appending bytes. This is a writer boundary, not validation of externally edited segments. Older/raw writers remain outside this version's mutation lock.

Truth-changing operations require a person-run generation migration and their own payload/reducer contracts. No reader inventory, announcement or successful compatibility check permits them in shared-v1 segments. The generation profile enables exact-entry `prune` and local exact-entry `vault_link`; `correct`, `lift`, `consolidate` and `group` remain blocked. `OP_CONTRACTS`, `V1_OPS` and `assertSharedV1Op` retain their shared-v1 meaning. The separate `GENERATION_OP_CONTRACTS` declares the enabled generation contracts and names `validatePruneRow` and `validateVaultLinkRow` as their runtime validators. Metadata alone never grants writer authority.

For shared v1, C05 remains a declared ceiling: expiry removes derived rows using the wall clock without a durable prune operation. Moving the clock backward can leave the incremental index empty while a rebuild restores the authored row and its edges. C02 has a generation counterpart: a live generation handle hashes only appended bytes but still reads and compares the whole prefix of a changed segment to catch rewrite-plus-growth, so a changed refresh costs O(segment) I/O (about 13 MB and 247 ms p50 at 20,000 entries in the [read receipt](bench/p9-generation-read.md)). Unchanged segments cost no data I/O. The upgrade, measured first, is a per-block hash chain or a tail window plus an inode/size check.

## Generation-only prune

The generation layout, selector, one-way bridge and coordinated rollout are bound by [agent-mem issue #9](https://github.com/STAIxBWLB/agent-mem/issues/9), revision 2. Existing v1-equal authored rows keep their schema and IDs. All writes by a generation-bound handle stay under `M/generations/G/`, with a separate Git repository and `refs/heads/amem/gen/G`. Legacy directories, index, machine identity and `main` remain untouched. A handle stays bound until closed; a selector change does not reopen running hub stores.

Prune rows use `agent-mem.prune/v1`, actor `person`, a generation ID, canonical authoring time/cutoff, machine, local/synced placement and sorted full-ID targets. Each target carries the full SHA-256 of its canonical authored row including id, expiry and exact basis row/hash. The prune row's own id is the first 32 hex of SHA-256 over the complete canonical payload excluding id. `validatePruneRow` rejects extra/missing nested fields, invalid IDs/hashes/times, unsorted/duplicate targets, more than 32 targets or a row over 16 KiB UTF-8.

Only serialized deadlines qualify: a note must carry its own canonical `expires`, or its demote/settle basis must carry canonical `by`. An implicit `at + 180 days` backstop or an instance TTL fallback is ineligible. A person can first author an ordinary v1 demote/settle with an explicit deadline. The person-authoring boundary checks effective observed expiry against its full captured state; a replica verifies target/basis identity and the explicit witnessed deadline. It cannot prove the author knew every later/offline deadline, and no private/global frontier is published to claim that completeness.

`exact-entry-v1` masks only the listed full target IDs. A same-ID replay remains gone across clock rollback and later deadlines. Another ID is independent even when text matches or it is a later promotion of that entry. Missing promotion ancestry alone never quarantines ordinary synced notes. Retained raw promotion metadata still hides a short-term source when its promoted copy is tombstoned. A pruned replacement remains permanently gone when evaluating supersession, so rolling the clock backward cannot hide its predecessor again. Get/alias/graph-start resolution must not bypass the exact mask. Raw debug logs/dumps retain authored rows and are not evidence-only projections.

A prune received before its target or expiry witness is pending, not evidence. Wrong generation, placement, row hash or impossible expiry proof is quarantined/refused. Read-only projection calls never author prune. Generation raw rows are retained rather than deleted at wall-clock expiry, allowing full derived-table equality on rebuild; unpruned views may still change under clock rollback.

## Generation-only vault links

`vault_link` uses `agent-mem.vault-link/v1`. Its complete canonical payload carries a full exact note ID, SHA-256 of the complete authored note including ID, project, relative Markdown path, generation, authoring time, machine, person actor and local placement. Its own ID is the first 32 hex characters of the complete canonical payload hash excluding ID. The validator refuses extra or missing fields, changed hashes, noncanonical times, unsafe paths, foreign generations and public placement. The maximum payload is 4096 UTF-8 bytes; the path is bounded to 512 UTF-8 bytes.

Only the witnessed exact entry stops appearing in vault candidates. A different immutable entry remains independent. Missing or mismatched target witnesses cannot suppress a candidate. The curated note remains available as ordinary evidence, and raw authored rows are retained. The path is metadata: amem never opens, writes, indexes or copies a vault. There is no MCP link-write tool.

Current standalone policy and the stricter host policy screen candidates before selection, ordering, limits and counts. Link authoring rechecks the exact target ID/hash under the mutation fence, appends and fsyncs a complete local row, then refreshes the derived index. It refuses an incomplete prior tail. Complete rows replay and rebuild; a partial tail requires person inspection. Link rows remain local during sync and follow the target's owner through curated shard migration. The frozen writer fixture proves the ordinary evidence remains readable while candidate suppression survives rebuild; `test/vault.test.ts` covers policy, exact target boundaries and shard migration.

Published 0.3.1 is the exact-pinned pre-vault reader used by the compatibility fixture. Ordinary listing can keep working through the shared derived index already advanced by a P2 writer; a full rebuild rejects the unknown operation. An independent unadvanced index also refuses when refresh must parse that suffix. The fixture deliberately excludes the derived index to force that rebuild on open. Published 0.1.1 and 0.2.0 only establish shared-v1 isolation because they predate generation support; they cannot prove unsupported-generation refusal. These are synthetic compatibility receipts, not verification of installed readers or a live rollout.

Do not record vault links on a memory home used by a 0.3.1 host, including agent-hub while its exact pin remains `@staix/agent-mem` 0.3.1. Upgrade the sharing host to a pin that includes P2 vault-link support before authoring the first link. A successful ordinary list through the older host is insufficient: its next rebuild will refuse that generation. This guard does not authorize installation, a restart or a real-home mutation.

## Plans, privacy and recovery

The local plan envelope is `agent-mem.prune-plan/v1`, with generation, selector revision, host-bound project and policy revision, ordered `{placement,payload}` rows, counts, `hasMore` and a SHA-256 seal over its canonical bytes excluding seal. The selector revision is a canonical selector hash or `absent`. Limits are 256 KiB before parsing, 16 rows and 256 total targets, plus per-row limits. Automatic planning chooses a deterministic full-ID prefix and reports `hasMore`; explicit oversized target requests refuse. The seal detects changes, but grants no authorization. Apply rechecks person intent and bound generation/machine/selector/project/policy; every not-yet-durable row must also pass exact target/basis hash and current observed-expiry checks before journal/append. Completed immutable row IDs are resumed as durable receipts rather than reauthorizing their tombstones against a later deadline.

Standalone amem authors local masks only, including masks over synced notes. `--policy-free` cannot authorize a synced prune. The host's public policy must attest the exact normalized row hash, generation, project and current policy revision; target and basis must already be public generation rows or verified cached legacy-main witnesses. Unpublished legacy-root logs, local/private bases and private/unknown classifications remain local. No private IDs, closure hashes, private counts or local aggregate seals enter synced rows, errors or public receipts. Detailed plan counts and receipts are person-local. A policy refusal/change invalidates the plan; no silent repartition occurs during apply.

Apply persists and fsyncs the exact local plan before authoritative rows. Under the generation mutation fence it appends complete rows and fsyncs before refreshing the index. Atomicity is per row; local/public partitions are not one transaction. Resume skips durable IDs and completes a partial own tail only when its existing bytes exactly prefix the same persisted planned line. Mismatched tails refuse; complete log lines are never truncated or rewritten. An index failure is recoverable from durable rows.

Migration activation uses the home-wide PID/signature `profile.lock`, captured source-prefix receipts, staged rebuild validation and fsynced metadata; selector replacement is the last commit point. Resume keeps the same G. Corrupt/missing active state blocks rather than silently falling back to shared v1. Deactivation retains both histories and intentionally omits generation-only notes/prunes from the selected v1 view. It is not a lossless rollback.

Explicit deactivation validates the selector but does not require a valid generation descriptor, seal or directory. It switches back under the profile lock and retains all data; a healthy existing generation mutation fence is respected. Normal selection keeps failing closed on corrupt active state. Crash fixtures interrupt after seal, before and after selector replacement, and reopen after the first generation append.

Malformed complete legacy lines are skipped and counted in both migration modes and person-local status. Unknown operations and content-ID mismatches are malformed legacy input; they do not block later valid rows. Generation-authored segments retain strict validation. Prefix rewrites/truncation and non-fast-forward legacy input remain fatal. `MemoryStore.bridgeStatus()` returns only the skipped count, and standalone human CLI output includes it; model-facing raw-command callers do not receive the optional status callback by default. JSON note arrays are unchanged. Generation settlements and promotions affect generation-born identities only; a bridged identity keeps legacy birth even if its same immutable ID is replayed into a generation segment.

A settlement row witnessed in both legacy and generation input retains both source-presence bits, so replay order cannot move a deadline from one projection to the other. Legacy birth wins conservatively for duplicate note identities. Generation segment counts include the bridge's consumed inputs, so a rebuild receipt cannot report zero segments for a nonempty bridged home.

Shared-v1 sync uses its unchanged direct Git spawn and caller Git configuration environment. Only generation sync uses the separate environment-isolated, child-umask invocation. The prune CLI opens its plan once without following a symlink, validates that descriptor with `fstat`, reads at most 256 KiB plus one overflow byte, and refuses growth, truncation or invalid UTF-8 before store access.

## Rollout and unverified legs

This source implementation neither migrates real memory nor proves deployment. Before real migration, a separate agent-hub task must exact-pin the released generation-capable package and bind store consumers, sync, sidecars and host policy to the same profile. The person's installed amem and running hub must prove matching canonical home/G/selector revision and loaded package through a synthetic cross-write/read/prune preflight. Quiesce and close known local handles before separately approved real migration, then reopen and verify running bindings before resuming writes. Old/unsupported or differently configured consumers must refuse visibly; on-disk package metadata alone is not running-store proof.

Candidate/counter sidecars are not migrated or synchronized. The standalone `amem review` CLI accepts general memory candidates through the selected generation or project shard with current standalone policy. Older correction/failure candidate paths retain their profile-aware integration guard. Host rollout, installed-session preservation, real-home migration, real multi-machine sync and host recall/brief/ask/capture/PII-turn receipts remain open live gates. Synthetic fixtures do not close them.

Complete parsed prune bytes are not a durability receipt. Apply always crosses the append hook's fsync fence, even on an idempotent resume. A private per-segment pending claim binds plan seal, row ID, expected byte offset, prefix hash and planned line hash before append. Only that plan can complete a partial tail; ordinary generation writes and public sync refuse an outstanding relevant claim. Files and containing directories are fsynced before completion. Local metadata writers enforce the same 256 KiB byte limit as their readers before opening a temporary file.

Explicit legacy fetch/sync verifies Git history and captures immutable legacy-main blobs plus an atomic plain-file manifest. Normal bridge reads use that captured input and never spawn Git. Segment checkpoints retain size/inode/nanosecond time metadata alongside their verified prefix hash. Unchanged input, including a reopened handle, reads and hashes no segment bytes. A seeded live handle uses SHA state copies to hash appended suffixes only; on a changed file it still reads and compares the old prefix, so prefix rewrite plus growth remains fatal. This does not claim suffix-only disk I/O. A cold handle that first finds a changed segment verifies/seeds the complete prefix once; an explicit rebuild verifies full input. The cold O(segment) path is a declared ceiling, with serialized hash state or per-block receipts deferred until measurements warrant them.

Only newly completed suffixes are parsed/applied. Initial migration receipts verify input but never substitute for consumed rows in a recreated derived index. A captured-input transaction verifies its checkpoint frontier before commit and retries boundedly if another handle advanced it; it never rolls the shared watermark backward. Prune targets and row projections are read from the same WAL snapshot. The synthetic read receipt separates warm unchanged, unchanged reopen, seeded live append and cold changed cases; it does not establish a before/after speedup or live-home latency target.

## MCP candidate reads (#13, task #209)

`amem_search`, `amem_timeline` and `amem_show` do not refuse because a tier exceeds 5,000 rows. They read at most 256 candidate bodies per SQL keyset page. Exact startup-bound project identity, `since`, chronological/anchor ordering and the query predicate run inside the derived query. Curated relations still fold over complete lifecycle metadata so forgetting, supersession, promotion, expiry and generation masks retain their existing semantics; only candidate bodies are materialized. Cold curated FTS reconstruction streams bodies into the existing derived cache.

Search ranks the newest 5,000 permitted matching candidates per tier. Raw FTS is a match predicate, never a BM25 preselection: each complete row passes current standalone and host policy before it consumes that public candidate window. Denied or invisible rows cannot exhaust the public window. BM25 and tier/recency weights are computed in a temporary FTS index containing only screened candidates. This is a bounded recent matching window, not a claim of globally best ranking over an arbitrarily large history. `since` can narrow the window; a policy-bound persistent ranking index is a future upgrade. Without FTS, or when lazy capture indexing is absent or contended, paged substring matching retains the explicit fallback engine. The first capture page chooses and pins that engine for the entire search, including an empty page. Both tiers apply complete-row policy and true substring matching before candidate caps; no curated FTS predicate or temporary FTS ranking runs during fallback. A later independent read retries lazy initialization after contention clears.

Capture's independent derived `mcp_fts` indexes the same body MCP searched before this change: excerpt, decoded paths and event. It uses the same tokenizer as public ranking, including Korean particle variants, Unicode case and diacritics. The existing library excerpt-only `fts` remains separate. Capture hooks and append never create or backfill `mcp_fts`. Only a queried MCP read lazily creates its table, triggers and historical SQL backfill in one immediate transaction. That snapshot covers all pre-initialization appends; after commit, triggers keep it level across append, replay, update and eviction. Timeline, show and capture-disabled search never initialize it. The MCP read accepts this one-time indexing cost; R2 hook admission does not. Neither changes authoritative capture rows or curated schemas, hashes, segments or paths.

Timeline resolves and screens an anchor directly, even outside a recent search window, then pages nearest or latest rows until each tier has enough permitted entries. `since` restricts the neighborhood, not anchor lookup. Point/prefix reads use the same lifecycle and policy checks; ambiguous permitted prefixes return no row. No foreign shared-project note is admitted. The graph complete-history ceiling is separate and unchanged; work-list replay is described below.

The actual stdio resource script seeds 5,001 curated and 5,001 capture rows, plus 10,001 work-list appends reduced to 100 items. It checks search, capture-disabled and capture-only queries, time filters, latest and anchored timelines, work reads, R3 idle/peak RSS and EOF process reaping on both CI platforms. Synthetic homes are used; this is not a live cutover or a new release.


### Reviewed alias and curated rows (#27)

`aliases.jsonl` holds two op kinds: `alias` (`alias`, `key`) and `unalias` (`alias`). The latest op per alias key wins and nothing is rewritten, so an older reader that only knows `alias` ignores the removal line and shows its older view. `amem alias remove` refuses a key that is not aliased now.

For an aliased key the CLI and MCP exact-project filter widens to the canonical key plus every key aliased to it, for notes, goals, suggestions, search, timeline, show, vault candidates and links, candidates and counters, and work lists. Rows keep their own project in the log and read as the canonical key. The widening is opt-in through `StoreOptions.reconcile`, `CandidateStore({ reconcile })` and `WorkListStore({ aliases })`: the library default and `amem prune` keep the exact key, so a prune plan never names rows of a key it was not asked about. Under curated shards the aliased key's shard is opened read-and-own beside the canonical one (never created when absent), and a settle, forget, supersede or promote of an aliased row is appended to the shard that holds it. The MCP guard closes the session when the effective alias set changes.

Every write that copies a row keeps the key the row was written under, never the canonical label a reconciled read shows: a promote's long-term copy and a vault link name the raw project, so a raw-key reader, a non-reconciled host and the same note promoted on another machine all produce the same row and id. Known limits: (1) `aliases.jsonl` is not synced and an amem or hub older than this change ignores the `unalias` line, so it keeps binding the old key to the canonical one for capture, work lists and the MCP binding until it is upgraded; upgrade every host that shares the home before relying on `alias remove`. (2) A correction accepted on an aliased row is a new note under the canonical key, and its supersede op is appended to the shard that holds the old row. After `alias remove` the old key's shard shows the old note again, because the replacement lives in the canonical shard. This affects visibility only, nothing is lost, and the replacement stays readable under the canonical key.

### Hook upgrade regression (#13, task #327)

`test/capture-mcp-lazy.test.ts` seeds 5,001 maximum-length capture excerpts, removes only the derived MCP index to represent a pre-upgrade shard, and opens/appends through the ordinary hook store. Transparent SQL-call recording observes the real row insert and zero MCP-index statements on that hook path; the unchanged SQLite schema version and absent MCP table/triggers independently verify its effects without a load-sensitive timing assertion. A lazy read then includes both historical and pre-initialization appends; later inserts, updates and deletes retain index parity. A first open under a real SQLite writer lock returns bounded substring pages, and the same handle retries after release. ## Concurrent capture spool publication (#13 P3 prerequisite)

Contended capture appends publish one private, complete immutable segment per event in the shard's `spool/` directory. A unique process/sequence/random name is first written and closed in `spool/.writing/`, then atomically renamed into the readable directory. No writer appends to an inode a drainer can read. Each drain claims a segment by atomic rename to a unique `.draining-<nonce>` name. A recovery drainer may reclaim even a live claim; replay hashes each complete screened line into the existing unique `spool_id`, so competing readers and a crash after commit remain idempotent. A drainer only removes or renames its exact claim, never a fixed name another drainer can replace.

Large legacy files keep their immutable bytes. After the SQLite transaction commits, a rename acknowledges the consumed byte offset in the filename; a crash before that rename replays the prefix safely. Each invocation inspects at most 256 directory entries, claims at most 32 files, reads at most 256 KiB and inserts at most 1,000 lines, with a 25 ms admission deadline between files. This is a work bound, not preemption of an active filesystem or SQLite call. Complete newline-delimited rows cross byte windows without splitting UTF-8. A short leftover allowance defers the next incomplete row at the same byte offset; only a full 256 KiB window can mark a line oversized. An oversized malformed line is discarded through its next newline, counted once, and cannot hide a later valid line. Fixed `spool.jsonl` and `spool.jsonl.draining` inputs remain readable for upgrade; new appends never create them.

An upgrade must quiesce old capture writers: a newer reader cannot repair an inode still opened by an old shared-spool writer. A process killed before publication can leave an unpublished `.writing/` file; it is deliberately never replayed because its last row may be incomplete. Removing such files is quiescent maintenance. Power-loss durability of an interrupted append is not claimed; an fsynced journal would be a separate upgrade. Capture rows, screening, lazy MCP FTS, curated log schemas, hashes and segment paths are unchanged. Deterministic subprocess filesystem barriers prove both the stale-drainer deletion and already-open writer races; two concurrent identical writers with two drainers also retain both events exactly once.


## Complete work-list replay (#13, task #210)

Work-list reads have no persisted-operation count ceiling. The derived index stores a replay key for each row and streams its ordered cursor, keeping only the latest permitted scalar values per list/item field. Timestamp, import-origin, numeric source-id, same-machine append position and hash tie-breaking retain their earlier order, including JavaScript UTF-16 lexical order. Null clears a field. Current policy runs on every row before reduction and closed-list filtering; a failed policy never changes visible fields or state.

Each read pins a separate read-only SQLite snapshot before the mutation lock is released. A host policy may await while another writer appends; the initial read keeps its original frontier and a later read observes the append. Iterators and snapshots close on completion or error. The additive replay column is derived only: older derived indexes are upgraded, and rows indexed by an older writer are backfilled one at a time. Append-log bytes, hashes and public API signatures are unchanged; incremental and full rebuild results remain equal.

Memory is bounded by the current result's distinct lists/items/fields and a small SQLite reader cache, not an array of historical payloads. Reads still verify log bytes and examine the complete applicable history, so time grows with history; an enormous current result also needs its result memory. Paged materialized views are a future upgrade if measured usage requires them. The real stdio MCP budget fixture now includes 10,001 work operations and checks every item's latest progress with the existing idle <100 MB, peak <200 MB and EOF-reaping assertions.

- A staged hook capture of a project that is archived or forgotten is retired by the drain at once with the counted reasons `project_archived` and `project_forgotten` (see the hook spool contract), never left pending, so such a project cannot fill the home-wide spool.
- `openShardStore` is the one gate for every curated open, hub recall included: it refuses a project that is not active before it initializes or reads the shard, unless the caller passes `lifecycle: "ignore"` (the catalog's own count, export and `--include-archived` reads do). The user shard has no lifecycle. **Hub pin:** agent-hub gets this gate for free once it pins the amem release that carries it; until that follow-up lands, `hub_memory_*` and hub briefs of an older pin still recall an archived or forgotten project.
- The person's own project-local recall (`amem search|list|show|graph`, goals, prune) is gated by `curatedStore` on the bound project, split or not; `search --all-projects --include-archived` and `project export` are the explicit ways to reach an archived project.
- A writable `CaptureStore`, `sessionStartBrief` and `createMemoryMcp` refuse a project that is not active (the brief returns the unavailable result, MCP throws its generic unavailable error), and their binding guards re-check the state, so an op recorded mid-session takes effect at the next call. `CaptureStore({ lifecycle: "ignore" })` is for gc and export only and never appends.
- `runGc` opens only capture stores. Nothing in it reads or writes `log/`, `local/`, `work/` or an index of the curated tier (`test/usage-gc.test.ts` holds the shard's non-capture files byte-identical across a run).
- Cross-project reads are person commands. `searchAllProjects` and `vaultCandidatesAll` open one project's curated store at a time through `openCuratedForRead`, which never initializes a store, and write nothing under the home. Their replies carry `crossedProjects` and the projects read. MCP has no all-projects argument.
- `exportProject` bundles the project's capture, curated rows, goals and work lists, the work lists of a key aliased to it included (the reconciliation the CLI, MCP and brief use). It claims its destination with `O_EXCL | O_NOFOLLOW` (the existence check only gives the message), refuses a destination inside the memory home and a forgotten project, screens every value with the secret screen and the caller's policy, and removes only the partial file it created on failure.
- The R7 split (`capacitySplit`) takes only capture quantities (bytes in use, bytes per day, last capture time). Its caps are whole MB, sum to at most the budget, are at least 1 MB (a budget with fewer whole MB than shards is refused with `SplitBudgetError`, and `capacityReport` carries the reason as `splitRefused`), and never fall below a shard's current use unless the budget forces it (the row says so). When every shard's use fits but not every need, each shard gets its use first (whole MB, at least 1) and only the headroom is shared by activity and growth. A shard's retention is never shorter than its idle time plus 30 days, because gc counts age from now. `capacity apply --split` writes each non-forgotten shard's `config.json` and nothing else: the preview stores the target values, `--confirm` writes exactly those (never a recomputation), refuses a preview older than an hour or dated in the future, or one whose shards or current configs changed, and leaves out a shard that has no directory of this machine (named under `skipped`).

## Repo scope (#15 T4, D6)

- `.amem/log.jsonl` in the repository is append-only, one JSON line per entry, under its **own** schema `amem.repo/v1`. The `agent-hub.memory/v1` hash domain, scopes and kinds are untouched: no existing reader, sync ref or generation sees a new kind. A line is exactly `{schema, op:"note", id, at, kind, title?, text, about, actor:"person"}`, with `id` the first 32 hex of sha256 over the canonical JSON of the other fields (the `entryId` derivation, over this schema). It carries no machine, peer, task, project or source-entry id, so nothing about this machine or a private project is committed.
- Kinds: `decision`, `contract` and `fail` only. A finding stays private. Only a long-term note that is not superseded can be promoted.
- Entry only by `amem promote <id> --to repo --policy-free`. It is person-only (an agent marker is refused by the CLI, and a terminal on stdin is required, the preview included), and runs the full screen: the standalone policy (secrets, default PII, private paths, denied files), a home-directory or credential-location check (text folded first: `$HOME`, `%USERPROFILE%`, backslashes, case and Unicode forms count), and the repository's own `.agenthub/config.json` and `config.local.json` as data (`local.deny`, `pii.paths`; no agent-hub import). Those globs have **agent-hub's semantics**: `src/memory/path-glob.ts` ports `policyPaths` and `matchesPolicy` (`*`, `**`, `?`, a trailing `/` for a directory, a leading `/` anchoring at the root, case-insensitive, `includeParents` for the `about` links), and `test/fixtures/path-policy-parity.json` is generated from the hub's real matcher (`scripts/gen-path-policy-parity.ts`, hub commit 9fdea5b1: 14 patterns × 48 paths, with and without parents, plus the validation rows) and checked by `test/path-policy-parity.test.ts`. A list over 64 entries, a non-string entry or a pattern over the hub's length limit refuses by name. Ceiling: the match is lexical, so a symlink alias of a denied path is not discovered (the same limit the hub documents). A config file that exists but does not parse or has the wrong shape **refuses** the promotion: an unreadable deny list is never read as empty. The `about` links that name a task, goal, memory entry, absolute or escaping path are left out of the committed line and listed in the preview.
- Without `--confirm` it prints the exact line that would be appended and writes nothing. With `--confirm` it appends exactly that line. A line already in the file is a no-op.
- Visibility: every remote's **effective** fetch and push URLs (`git remote get-url [--push] --all`, which applies `url.<base>.insteadOf` and `pushInsteadOf`) are asked through the same check `sync` uses, `remoteVisibility`. That check accepts a URL only when its host is exactly `github.com` over `https`, `ssh` (user `git`) or the scp form (`git@github.com:owner/repo`), with no port, query or fragment and a well-formed `owner/repo`; anything else (`github.com.evil.example`, `evil.example/github.com/…`, an enterprise host) is `unknown`. `gh` runs with `GH_HOST=github.com` and the enterprise token variables removed, so a configured `GH_HOST` cannot send the question to another server. Only a repository whose remotes are **all** positively private is private (`internal` counts as private, as `sync` has always done). Public, unknown, no remote and a `gh` that cannot answer all need `--confirm --confirm-public <first 8 or more hex characters of this entry's id>`, per entry: a prefix of another entry, a short one or any non-hex value is refused, and there is no blanket flag. Credentials in a remote URL are never printed. This tightening applies to `amem sync` as well: in 0.6.0 sync recognised a GitHub repository by a loose pattern, so a lookalike host could be asked as if it were github.com (changelog).
- amem never runs `git add`, `commit`, `push` or any write command (`test/repo-scope.test.ts` runs a `git` shim and fails on any of them). The person commits the file through normal review. `.gitattributes` is touched only by `amem repo attributes --confirm` (preview first, idempotent, appends `.amem/log.jsonl merge=union`).
- The file is untrusted input on every read, because a pull request can add a line. `.amem` and `log.jsonl` are checked with `lstat` and opened `O_NOFOLLOW`: a symlink, a directory or a device is `unsafe` and reads nothing. A read keeps the **newest** 1 MiB (whole lines only; an over-cap file loses its oldest lines, reported partial), a line is at most 16 KiB. Order is file position, newest appended first, never the line's own `at`: a line dated in the future cannot pin a list or a brief, and its shown `at` is clamped to now. A line with an unknown field, the wrong schema, kind or shape, a control character (anything in C0 or C1 except tab and newline: a pull request cannot carry a terminal escape into `list`, `search` or `show`) or an id that does not match its content is skipped and counted; duplicates collapse to the newest copy (`merge=union` can repeat a line); a valid line that names a secret, personal data, a home path, a credential location or a denied path is withheld and counted. `readRepoScope(root, policy, {limit?, remainingMs?, reserveMs?})` stops, reported partial, at `limit` entries or when `remainingMs() - reserveMs` is spent, so a caller with a deadline reads the newest few rows and not the file.
- Recall (D4, AC3): `amem list|search|show`, the MCP `amem_search|amem_show` and the session brief include the **bound repository's** `.amem/log.jsonl`, and only when that repository's own project key resolves to the bound project. A server or brief bound to project B and started inside repository A reads nothing of A's. `--all-projects` adds no repository rows. Repo rows are `evidence: false` (reviewed repository content, not the person's own curated note) and are screened by the caller's policy plus the repository's own deny list; a broken repository config withholds them and the brief and CLI say so (`repo=unavailable`).
- The brief's coverage header gains `repo=<state>` only when the repository has a log, so a brief for a repository without one is byte-identical to before. Every brief path (native hook or not) first asks by `lstat` alone (`repoLogNearby`: a few syscalls, no git) whether a `.amem/log.jsonl` exists at or above the cwd, and only then pays the git calls that resolve the root. The SessionStart hook (which sets `projectFromCwd`, because it resolved the project from that very `cwd`) then finds the root by `lstat` alone (`nearestRepoRootWithLog`: the nearest ancestor with a `.git` entry, file or directory, must hold the log) and spawns no git at all (two synchronous git processes and their `rev-parse` and `remote get-url` output stay off the hook's deadline; this is a saving, not a fix for a budget breach). Every other caller (the CLI, the MCP server, a brief for a project it did not derive from the cwd) still resolves the root with git and requires the repository's own project key to be the bound project. Ceiling: the hook's lookup is lexical, so a directory with a `.git` entry that git itself would skip (an invalid repository) can supply the log of that directory; the log is the cwd's own tree and passes the same screen. The section reads the newest `SECTION_RECORDS + 1` rows and passes the hook's own `timeRemaining` with a 20 ms reserve, so a 1 MiB log costs the hook the few rows it shows and never its budget (`test/repo-scope.test.ts`, the 1 MiB brief test; `scripts/measure-hooks-budget.ts` runs the real `amem hook SessionStart` against a 1 MiB log, p95 about 100 ms against the 150 ms limit, in CI on both OSes). Inside the native hook's 140 ms the optional sections are dropped as `deadline exhausted` when under 80 ms is left; that is the existing fail-open design and shows as `repo=unavailable`.
- The writer and the reader share one validator: `planRepoPromotion` refuses a title over 200 **bytes** or text over 4000 bytes (not characters), and refuses any line the reader's own `parseRepoLine` would reject, so a promotion that reports success always shows up in recall. On the MCP FTS engine the repo rows are selected by FTS like curated ones (punctuation and extra words do not drop a hit); the substring-AND filter is the fallback engine's.
- Ceilings: no `amem repo` command removes or edits a line (a change is a reviewed commit); one `.amem/log.jsonl` per repository root (a submodule's file belongs to the submodule); the visibility check needs `gh` and is `unknown` for a non-GitHub host, which asks for the per-entry confirmation; promoting into a repository whose `.gitignore` or `info/exclude` ignores `.amem/log.jsonl` writes the line and prints a warning, because `git status` will never show it; the append checks `.amem` and the file with `lstat` and opens with `O_NOFOLLOW`, but another process with write access to the repository could still swap `.amem` for a symlink between the check and the open (a `ponytail:` comment names the upgrade: `openat` against a directory descriptor).

## Per-shard private sync (#15 T3)

`amem sync --policy-free` selects only the opened canonical project and its user overlay. Each uses its own stable private-remote ref, `refs/heads/amem/p/<key-hash>` or `refs/heads/amem/u`; machine stores and unopened projects are never fetched. Reviewed aliases stay local. Immutable content-addressed packs contain complete original canonical payloads, IDs and attribution, not indexes, machine identity files, capture, candidates or work lists. Imports rebuild local derived views. Shared-v1 and unsplit-generation sync retain their existing transports. No resident job or network work is added to capture or read hooks.

Placement decides transport; `publicWitness` decides prune proof. A hash/seal-verified legacy `log/` original whose coalesced placement is `synced` may travel even if it has never synced before. An unwitnessed original already covered by a local tombstone is excluded from first publication; already witnessed originals retain the existing transport behavior. Legacy-local originals, short notes, settlements and rows with coalesced local placement do not travel. Exporting a row does not set `publicWitness`; only the existing reducer over a verified fetched public occurrence supplies that evidence. A prune with an unwitnessed legacy target or basis remains invalid or pending.

All selected refs and complete reachable histories are validated before publication/import: exact realm descriptors and paths, immutable append-only packs, original row hashes and complete per-realm prune witnesses. Blob bytes must match their Git object ID as well as their recorded size, so text-pipe whitespace normalization cannot conceal different remote bytes. Public or unknown remote visibility refuses, as do differing/multiple push destinations, symbolic refs and rewritten ancestry. Fetch uses only exact selected refs with no tags; atomic push uses no follow-tags. The existing host/`GH_HOST` privacy checks and hardened Git runner are reused unchanged. Errors fail open with one shard-labelled or neutral reason. A cancelled or refused preflight appends no selected public rows and publishes no refs.

Interrupted imported prunes resume only from an exact validated one-row transport plan and native append claim bound to the current project/user realm, generation and selector. Preflight reads their metadata and verifies the complete prefix plus any partial canonical-row bytes without appending. The row must match a verified fetched prune and pass all selected realms' complete proof checks; only after successful atomic publication does the existing idempotent append resume with the original line and seal, fsync and clear the claim. Plan-only, pre-append claim, partial-tail and complete-but-unacknowledged crashes preserve exactly-once tombstones and rebuild parity. Unrelated person-authored plans, bad seals, stale bindings, unmatched fetched rows and altered prefixes remain refused, with no eager repair or log rewrite.

A replacement remote missing a previously synced selected ref is refused as `previously synced remote ref disappeared`. Restore the original remote with `amem sync --policy-free --remote <original-private-url>`, or seed the positively private replacement with the selected refs and their complete histories from the original before retrying; do not delete the local transport cache or substitute empty history.

Owned shard-cache Git invocations disable automatic maintenance and garbage collection for that invocation only, including transient-ref cleanup. A background Git maintenance process can otherwise remove `objects/maintenance.lock` between the strict cache walk's enumeration and `lstat`; the filesystem and indirection checks remain unchanged. Cache objects are retained without automatic compaction. Any manual maintenance requires every user of that cache to be quiesced; a future controlled compaction path must hold the existing transport mutation and sync locks. Unexpected errors still return the neutral `shard sync unavailable` result without default logging; only an explicitly supplied internal test observer can inspect the original exception, and it is not exposed through `SyncOptions`, the CLI or environment flags.

`ponytail:` foreign-generation prune rows refuse the whole selected sync before append or push. Because `amem/u` is selected on every sync, one foreign-generation prune of a shared row blocks sync for every project on machines of another generation. Ordinary original rows cross independent generations, but full AC4 with cross-generation tombstones is not met; generation-compatible tombstone proof needs a separate schema/design decision. Manual sync audits selected reachable history and retains decoded selected packs in memory; an incremental verified audit cache is the upgrade path. No arbitrary lifetime history cutoff or row omission hides those ceilings.

## Standalone policy configuration and hub-neutral surface (agent-mem#40 F1, F4)

- **Where the policy comes from.** `amem.config.json` in the memory home (machine-local), narrowed by an optional `<repository>/.amem/config` found by walking up from the working directory to the nearest `.git` entry (`lstat` only, no git process, 32 levels). Both are bounded plain JSON read through one descriptor with `O_NOFOLLOW`; a link, a non-file, more than 64 KiB, an unknown key or a bad value is an error naming the file, never "no policy". `src/memory/config.ts` is the one reader (`loadAmemConfig`, `configuredPolicy`, `configuredPolicyOptions`).
- **What it holds.** `denyPaths` and `piiPatterns` (at most 64 literals of 256 bytes, no control characters, never regular expressions), `briefBytes`, `excerptBytes`, `capturePaths` and `capture.{capMb,retentionDays}`. The three counts can only lower the built-in ceilings (`HOOK_CONTEXT_BYTES`, `CAPTURE_MAX_EXCERPT`, `CAPTURE_MAX_PATHS`). `capture.*` is the lowest layer of the R6 bounds: a shard's `config.json`, then the home's `capture-config.json`, still override it.
- **Narrow only, and applied where the working directory is known.** `CaptureStore` takes `cwd` and reads that repository's `.amem/config` (found by `repoConfigRoot`, no git process); the MCP server, `amem ingest`, the brief and its worker, and hook staging pass it. A `CaptureStore` opened without `cwd` (a library caller, `gc`) applies the machine file only. A library caller's own `excerptBytes` or `capturePaths` can only tighten the configured value (the lowest of the defined values wins), never loosen it. The repository file takes `denyPaths`, `piiPatterns`, `briefBytes`, `excerptBytes` and `capturePaths`. Its lists are unioned into the machine's; a number counts only when lower than the machine's (or the machine has none). It cannot remove an entry, raise a budget, move the home or touch `capture`: those keys are errors. A host policy passed through the library (`StandalonePolicyOptions.host`) is composed in, never replaced, so the result declines whatever any layer declines. `StandalonePolicy.screenStandalone` is the synchronous standalone part only (secrets, default PII, configured patterns, deny paths) for callers that cannot await, such as the store's promotion screen; it never asks the host.
- **Enforcement points.** Capture: `CaptureStore` (every writer, hook, ingest or library) screens each excerpt with the configured patterns and filters paths with the configured deny list; the hook staging path (`stageHookCapture`) and the drain use the configured policy. MCP (`createMemoryMcp`), the SessionStart brief (`sessionStartBrief`, its worker and the hook), `review accept`, `promote`, `import`, repo promotion and the vault-candidate listing use `configuredPolicy`. Sync: `syncMemory` screens what it would publish, before any profile's sync starts, and refuses the whole sync, naming ids and never text, on a declined row, an unreadable or oversized source or a line that does not parse (an unscreened row must not pass because the scan gave up). A single-log home reads this machine's own segment. A generation or sharded home reads its verified snapshot's synced rows that are this machine's own or bridged from legacy input (after a shard migration those sit under `legacy/log/`, not in the machine's `log/` segment), for the opened shard and its user overlay. The policy is the machine's configured one plus `SyncOptions.screen`, which `amem sync` fills with the repository-narrowed policy, so a repository's `.amem/config` binds sync like every other command; a library caller that omits `screen` gets the machine policy only. Every row kind in the segment is read, not only notes: a goal's title and milestones sync too, and the screen covers every field except the ones the library generates (ids, hashes, times, op and enum names, machine and actor ids), so a text field a later op adds is screened rather than skipped. Other machines' rows are not read: they were screened where they were written. `--policy-free` stays accepted and never bypasses any of this (agent-mem#40 F4; the `AGENTS.md` rule that required it is amended to match).
- **`<private>` spans.** `stripPrivateSpans` and `stripPrivateDeep` (`src/memory/private-spans.ts`, a leaf with no imports) drop `<private>...</private>` before anything is screened, counted, hashed or stored. Tags match the way an HTML reader would: case-insensitive, attributes (`<private class="x">`), whitespace (`< private>`) and a self-closing `<private/>` (which opens a span like any opening tag); nested spans close from the inside, an unclosed span drops the rest, a stray closer and `<privateer>` stay as text. It runs at every write boundary, not only capture: `normalizeCaptureFields` (so the hook record, the spool and the store see the stripped text; replay re-normalizes with the built-in caps, the ceiling, so a record staged under a tighter cap still verifies), `CandidateStore.put` (before the input is validated or hashed, so the candidate id is the stripped one), `WorkListStore.write`, and the curated store's `append`, `withAcceptedNote`, `importNote` (whose duplicate lookup compares the stripped text) and goal rows.
- **`--policy-free`.** Still accepted by `promote`, `import`, `sync`, `review accept` and `project export`, and now ignored: those commands apply the configured policy instead of refusing without the flag. It never bypassed the secret screen or the sync remote's privacy checks. The prune contract above is unchanged: no flag enables a public prune.
- **The home.** `AMEM_HOME`, then a pointer `amem.config.json` in the default home (`~/.agenthub/memory`, or `$AGENTHUB_HOME/memory`) that carries `home` and nothing else (policy beside `home` would be silently lost, so it is an error), then the default. One level only: the redirected home's own file cannot redirect again. `amem status` prints `{ home: { path, source }, config: { machine, repo, ... } }` ahead of the unchanged migration fields.
- **The surface.** No message in the library names a host. `PERSON_ONLY` points an agent at `amem mcp` and the person at `amem review`; `--help` and `--version` (alone) work in an agent shell and every other command keeps the honest-session refusal. The memory and goal commands take `names: { memory, goal }` (default `amem`, `amem goal`) so a host that exposes them under its own name passes it; `memoryUsage(name)` and `goalUsage(name)` build the usage lines. `amem goal link` without a host task board refuses by saying amem alone has none. The `no sync remote` prefix of the sync refusal is unchanged (agent-hub matches it).
- **Fails closed.** A malformed `.amem/config` (an unknown key, a bad value, a link) makes `loadAmemConfig` throw, so `createMemoryMcp` refuses to start and a command run in that repository refuses with the file named; amem never serves unscreened because a policy file was unreadable. The cost is that a broken repository file disables amem there until it is fixed or removed.
- **Ceilings.** The deny and PII lists are literal substrings, so a determined spelling (extra characters, another language) passes; they are a floor under the person's own care, not a classifier. Sync is all-or-nothing per machine segment (no per-row skip). The repository file is trusted as the repository's owner's choice to narrow: a malicious repository can only make amem capture less, never more.

## Recall evaluation (F13)

`amem eval` (agent-mem#40 F13, AC7) measures the ranked `store.search` against a question set: BM25 with tier (short 0.9, long 1) and recency (a 30-day scale) weights, the ranking the MCP `amem_search` tool and hub recall use and the one #13 AC4 measured. It is NOT the `amem search` command, which is `store.list({ q })`, a substring AND filter newest first; the report header says so, and whether `amem search` should move to the ranked search is a separate decision. It is read-only, person-only like every ordinary command, and uses no model, network or embedding. `src/memory/eval.ts` is an import-free leaf (parser, metrics, text); `src/memory/eval-fixture.ts` seeds and searches a store.

- **Set format** (`schema: "amem.eval/v1"`, strict: an unknown key anywhere is an error). `questions`: 1 to 500 of `{ q, expect }` (`q` up to 500 characters, `expect` 1 to 20 names). `entries` (optional, up to 200 of `{ key, title?, text, kind?, tier?, about? }`, text up to 4000 characters, control characters refused, keys unique and `[A-Za-z0-9._-]`). With `entries` the set is self-contained and `expect` names entry keys (an unknown key is an error). Without `entries`, `expect` names real entries of the bound project by full id or by a prefix of 8 or more hex characters. A file is a regular file of at most 1 MiB, read through one descriptor whose size is checked before and after and whose bytes are bounded and decoded strictly as UTF-8.
- **Where it runs.** A self-contained set is seeded as notes into a throwaway store (`entries[].tier`, `long` by default) under a fixed clock that moves one day per entry, long-tier entries first and short-tier ones last (a short-term note leaves the index 14 days after it is written, and the clock stops a day after the last entry, so the short ones written in that window are live; one that has expired is reported as not in the store, like any other missing entry), and the store is deleted afterwards on every path; the memory home is never read or written. The clock makes recency and both tier weights count. A set without entries searches the bound project through `curatedStore`, curated tier only (the capture tier is machine-local recall, never an answer key), up to the largest `k`.
- **Resolving names.** In a real store each expected name is resolved by `store.get(name, project)`, memoized for the run (a name repeated across questions is looked up once), so a `mem:<id>` form, a prefix of 6 or more characters `get` can place, an id older than any list cap and a promoted short-term id (which names its long-term copy) resolve as `amem show` resolves them. The set parser accepts `mem:<id>` and 8 to 32 hex characters; a prefix `get` cannot place is checked against every visible id (uncapped). The resolved entry is then followed to the one that is LIVE: a superseded entry points at its replacement, and `store.search` returns only live entries, so an expected id that was superseded stands for the head of its supersede chain (an id whose chain loops is "not in the store"; if the replacement is forgotten the store makes the old entry live again and the old id stands for itself). More than one distinct live entry behind a prefix is refused with an error rather than credited to whichever matched, and two names for the same live entry count once. Coverage stays out of ranking this way: an expected name is "present" only if search could return it.
- **Metrics**, over the ranked list of distinct entry ids cut at `max(k)`: `hit@k` is the share of questions with an expected entry in the first k; `recall@k` is the mean over questions of (expected entries in the first k) / (expected entries); `MRR` is the mean of 1/rank of the first expected entry, 0 for a miss. `--k` is ascending unique integers 1 to 100, default `1,5,10`.
- **`all` and `answerable`.** A question whose expected entries the store does not hold can never be recalled. It scores 0 in `all` (what a person would experience: the denominator is every distinct thing it wanted, present or not) and is left out of `answerable` (what the ranking alone achieved: scored over the distinct entries the store does hold, so a name the store lacks never halves a recall), so the match-mode and coverage causes of P0 section 3.2 stay separate. An aggregate with no question in it is `null` (`n/a` in text), never a measured zero. The text report names the count and lists each miss.
- **Reading the fixture.** The built-in set (`src/memory/eval-set.json`, shipped in `src/` so an installed copy runs it, found with `fileURLToPath` so an install path with a space or non-ASCII characters works) is 26 invented harbour entries, five of them short tier and a twin pair that only recency and tier can order, and 32 questions including paraphrases and no-match ones on purpose so the numbers have headroom. `test/eval.test.ts` pins its scores for the current search. A lexical change from F14 ships only with an eval gain: it raises those numbers in the same PR. The fixture says nothing about a person's own memory; the P0 recall@10 of 0.52 against the 0.80 margin (#13 AC4) is measured on the person's own set through `--set`.

## Lexical recall changes are gated by eval (F14, AC7)

agent-mem#40 F14 asks for query expansion from aliases and tags and for BM25 plus 1-hop graph neighbours, each adopted only if `amem eval` shows a gain. The outcome of this change is that **none is adopted**: `store.search` is unchanged, and what ships is the gate that decides, the second fixture set and the record of what was measured.

- **What "aliases and tags" can mean here.** amem has no term-synonym aliases and no tags: its aliases are project-key aliases (`aliasedKeys`), unrelated to a query's words. The nearest real data is a note's `about` nodes (`path:`, `symbol:`, `issue:`, `task:`), which are already indexed in the body and kept as graph edges. The expansion candidate therefore adds the words of the `about` nodes whose own words the query already names, derived from the store with no configuration. A person-authored synonym list would be a new `amem.config.json` key and its own change.
- **The gate** (`scripts/f14-gate.ts`, `bun scripts/f14-gate.ts [--json]`) scores each candidate ranking with the same code `amem eval` runs (`evalSeeded`, with the candidate as its optional `rank`), on the built-in set and on a held-out set (`test/fixtures/eval-heldout.json`: 28 invented library entries and 37 questions, none shared with the built-in set). The held-out set was written and committed before any candidate was run and is never tuned on, because the built-in set was written before F14 and can be fitted by accident. `adopts()` says yes only when a candidate raises MRR or hit@1 on every set and lowers MRR, hit@1 or hit@10 on none; equal is not a gain, and helping one set while hurting the other is not adopted.

## Person notes and pending-review visibility (F6, F7, AC4)

- **`amem note add`** (`src/memory/note-add.ts`) writes one note with `peer: "person"` and `source: "person"`, so it is person-only: an agent marker is refused before the command runs and a terminal on stdin is required. That is the same gate as every other mutating command, and an agent that drives a pseudo-terminal and strips the markers passes it, exactly as it passes the others; the gate is a guard against the honest agent session, not authentication. `-` reads the text typed on that terminal until end of input (a pipe cannot reach it), which differs from a literal reading of "from stdin". `kind` defaults to `finding`, `tier` to `long`, `scope` to `project`. Text is at most 4000 characters, a title one line of at most 200, NUL bytes are refused, and `<private>` spans are dropped by the store's write boundary. The configured policy (machine file narrowed by the repository's `.amem/config`) screens the title and text before anything is written; a refusal names no text.
- **Structured `fail`.** `--approach`, `--symptom`, `--cause`, `--evidence` (repeatable, at most 16) and `--retry-when` are all required for `--kind fail`, each at most 1000 characters, and free text is refused with them. The body is the five labelled lines `Approach:`, `Symptom:`, `Cause:`, `Evidence:` (comma-joined) and `Retry when:`, the same lines an accepted `fail` candidate gets, so search and the plan guard read one shape. Every line-break character (LF, CR, VT, FF, NEL, U+2028, U+2029) inside a field collapses to a space, in `note add` and in the body of an accepted fail candidate alike, so a field cannot forge a label; a template that repeats a label is refused rather than keeping only the last. With no text and no field flag the editor opens the labelled template (`$VISUAL`, then `$EDITOR`, an empty `VISUAL` skipped, run without a shell: an existing path is one command even with spaces, otherwise quotes and backslashes split it with no expansion; on a private 0600 file in a 0700 directory that is removed on every path, including a signal-killed editor; SIGINT is ignored in amem while the editor runs so Ctrl-C reaches the editor and amem can still clean up, though a SIGKILL of amem itself can leave the text in the person's temporary directory; a missing, failing or signal-killed editor writes nothing).
- **The brief line.** `sessionStartBrief` reads the project's pending candidates (`candidate-pending.ts`, an import-light leaf: read-only SQLite, zero busy timeout, never creating, altering or pruning the database, failing open to no line) and, when some wait, emits `N candidate(s) pending, oldest expires in D day(s)` directly after the coverage header. It is reserved out of the same byte budget before sections are chosen and is left out when it does not fit, so the brief never grows and a brief with nothing pending is byte-identical to before. It carries numbers only, never candidate text or titles. `D` is the days until the soonest of them can expire, and an unshown candidate counts as shown now (so at least its 7 days).
- **AC4, no candidate expires unseen.** `candidates.db` gains a nullable `shown_at` column, added in place when a `CandidateStore` opens, inside one immediate transaction that rechecks the column (several processes open the store at once, every `amem mcp` among them; and the switch to WAL is retried for a bounded time on lock contention). An older database keeps its rows, all unshown; a reader without the column treats every row as unshown and the stamp is a no-op, which only keeps candidates longer. A pending candidate is stamped only by `amem review walk`, which refuses to run unless stdout is a terminal (a redirect to a file or a pipe would stamp candidates nobody saw), and only AFTER the candidate's header and body were written to it (a write that fails stamps nothing and asks nothing, so a candidate the person could not read is never counted as shown). The SessionStart hook, the brief and `amem review list` never stamp: the hook cannot know the person read the context, and `list` prints an id, a kind and a date (no content), is run by scripts and cron, and `--json` may be piped to a program, so a stamp there would start the 7-day clock with nobody reading. The first value is kept. The 30-day age expiry deletes a decided (accepted or rejected) candidate, or a pending one shown at least 7 days ago; an unshown pending candidate is kept however old. The 500-per-project cap keeps rows in three tiers, unshown pending first, then shown pending (owed its grace), then decided, so it evicts decided rows before a shown one and shown ones before an unseen one. `put` prunes, counts, inserts and prunes again in ONE immediate transaction, so concurrent proposers cannot all pass the count and then let the cap evict an unseen candidate; when 500 unseen ones wait it throws `CandidateQueueFull` (`code: "candidate_queue_full"`, no candidate text, worded for an agent: ask the person to review), which the MCP server maps to one fixed sentence instead of its generic refusal. Re-proposing an existing candidate is not new. The existing retention test is amended to this behavior.
- **`amem status`** adds `candidates: { count, oldestExpiresInDays, dueWithin7Days, unshown }` and a `warning` when any candidate is within 7 days of its 30-day age, or `candidates: { unavailable }` when `candidates.db` exists but cannot be read (the reader tries a plain read-only open, then an immutable one for a WAL database whose `-wal` and `-shm` are gone, and each form is proven with a query; the brief line fails open to no line). **`amem review walk`** writes each pending candidate (oldest first) to the terminal, stamps it, and only then asks accept, edit, reject, skip or quit, writing every outcome as it happens so an interrupted walk still shows what it did: accept runs the ordinary `review accept` (current policy, host shard checks), reject the ordinary `review reject`, edit opens the text (a `fail` candidate, and a general memory candidate proposed as a fail note, as the labelled template; a loose sentence is pre-filled under `Approach:`, while text that already carries any of the five labels opens exactly as written, so the edit cannot repeat a label), writes it through `note add`'s path as the person's own long-term note and rejects the candidate, skip leaves it pending, quit or end of input stops. Candidate text is printed with control and format characters flattened and bounded at 600 characters. A bare `amem review` still lists, so existing scripts hold.


## Doctor and ingest/sync cadence (F15, F16, AC8)

**`amem doctor [--json]`** is one report over the memory home, person-only like every other command (the agent-marker refusal runs first, so an agent shell never opens the home). Its sections, in this fixed order, each carry `status` `ok`, `attention` or `unavailable` (with a `reason`: a section that cannot be checked says so, never a silent zero), and the report carries the worst of them:

| section | what it says |
| --- | --- |
| `duplicates` | notes of this project whose kind, title and text are identical after case and whitespace folding (ids only, never text), plus the imported-duplicate groups `amem dedupe` previews |
| `stale` | notes whose every `path:` reference is gone from the repository (needs doctor run inside this project's repository, else `skipped`) |
| `candidates` | the pending summary `amem status` shows; `attention` when one is within 7 days of expiry. Doctor never stamps a candidate as shown |
| `capture` | per CLI (`claude`, `codex`, `kimi`, `pi`): `hook` `registered` (a setup receipt in the home's `setup/` directory, phase `applied`, naming that CLI) or `manual`; `capture` `fresh`, `stale` (older than 7 days) or `never`; the last capture time and row count. A registered hook that is not fresh, and any CLI that went stale, is `attention`; a CLI with no hook that never captured is reported, not flagged |
| `brief` | the SessionStart brief's real size for this project (`tokens`, `budget`, coverage), `attention` when partial or over 90% of the budget |
| `index` | the live index, snapshotted and brought level with the logs, equals a full rebuild of the same logs (both in the scratch copy). A curated split or generation home is `skipped` (its build already proves equality) |
| `readers` | reader leases of live processes, of processes that are gone, and unreadable ones. Doctor takes none itself |
| `policy` | the configuration in effect: which files, deny-path and PII-pattern counts, the byte budgets |
| `cadence` | per CLI how intake runs (`hooks`, `session end` or `manual`) and the sync schedule (below) |

**What "read-only" means.** Doctor writes nothing into the memory home: no file is created, changed, checkpointed or removed there, and it takes no reader lease. `test/doctor.test.ts` hashes every file of a populated home before and after the FIRST run (no warm-up), `-wal` files included; it normalises two kinds of SQLite bookkeeping and nothing else: a `-shm` file (wal-index scratch memory, which any read-only open changes) and an EMPTY `-wal` file. On Linux a database closed cleanly leaves neither, and a read-only open of it (the snapshot of the live index, the candidate and capture reads) creates them again, empty; macOS leaves them in place (Ubuntu CI showed this). A `-wal` holding data, every database, log, lock and sidecar are compared byte for byte, and the test first removes both so macOS takes the same path as Linux. A home nobody used stays absent, and so does a project the home has not seen. How:

- Every check that needs a store runs on a private scratch copy in a temporary directory, removed afterwards: the project's (and its aliases') curated logs, the lifecycle and alias logs, and the project's work logs in a base of their own. The first version opened the live store through `curatedStore()`; a review probe showed that rewrites `index.db` and `search.db`, checkpoints both WALs and writes a reader lease, and that the brief's work list recreated its lock file and re-ran its migration.
- The live shared-v1 index is only snapshotted (a read-only connection and `VACUUM INTO`), brought level with the copied logs the way the next reader would, and compared with a full rebuild of the same logs. A curated split or generation home builds and seals its index when it is created, so that section is `skipped` there (`amem rebuild` repeats the proof).
- The brief is measured with `sessionStartBrief({ measureOnly })`, used by doctor alone: it takes no reader lease, reads the curated rows from the scratch store and the work list from the scratch work base (a work log with no index is still counted, which the first version under-reported), and opens this machine's capture database read-only and only when it exists. Without a scratch work base the work section is `unavailable`, never `complete`. It measures the brief the SessionStart worker builds; the native parent's deferred brief is smaller and is not what is measured. The hook path does not set `measureOnly`.
- The scratch copy never outlives doctor (#435): Ctrl-C, SIGTERM, SIGHUP and SIGQUIT remove it and end doctor with that signal (SIGQUIT excepted: its default action is a core dump, which Bun honours, so a re-raised SIGQUIT on Linux wrote a 5.9 GB core file in a container with core dumps on while the shell waited; doctor exits with the status that death would have had, 131, instead), an `exit` handler covers a throw, and the next doctor sweeps copies a killed run left (name `amem-doctor-<pid>-<random>`, a plain directory this user owns, owner pid gone; an older unnamed one after a day). SIGKILL cannot be handled, which is what the sweep is for. Bun runs a signal handler only when the event loop turns and a git lookup is a synchronous call, so doctor yields to the loop between stages; `test/doctor.test.ts` stalls each git call it makes, one at a time, and signals doctor during it. The limit: a signal that arrives BEFORE a call that then hangs is handled only after that call returns, because nothing turns the loop while it hangs (a terminal's signal also reaches a git that was already running, which is the case covered; a git started after the signal is not signalled). Doctor's git calls are short lookups, so this needs a git that hangs, and the next doctor sweeps what such a run leaves.
- Duplicates and stale notes read at most the newest 100 000 notes of the project; a project with more says `truncated`. More than 64 MiB of logs is `unavailable`, not a partial answer.

`skipped` means nothing to check here, with the reason (no curated notes yet, not run inside the repository, a split home); it does not degrade the overall status. `unavailable` means a check could not run.

**`--json` is stable (AC8).** `amem.doctor/v1`. `test/doctor-snapshot.test.ts` pins every key, the type of every value and the fixed vocabulary against `test/fixtures/doctor-snapshot.json`, for a populated and for an unused home. Adding a key or changing a type or a word changes the fixture, so a reviewer sees it.

**F16, cadence without a daemon.**

- *Ingest.* Already done by `amem setup` (#417): the SessionEnd hook of Codex and Kimi, and Pi's `session_shutdown` extension, run `amem ingest <cli>` within the hook budget (3 s, 2.5 s for Pi) as a short-lived process with no watcher. Claude captures through its seven bounded hooks. Doctor reads the setup receipts and reports a CLI with no registered hook as `manual`, with the command to register it. "Registered" is evidence from the receipt (`hookEvidence: "setup receipt"`): a hook the person removed by hand afterwards still shows as registered until `amem setup <cli> --apply` or `--undo` runs again.
- *Sync (owner decision O3: off by default).* amem registers **no** sync hook and starts **no** resident process. `amem sync --if-due` is the opt-in entry the person calls from their own shell (for example an EXIT trap); it needs a terminal like every mutating command, so an unattended scheduler is not a caller. **A CLI's SessionEnd hook cannot run it, deliberately (claude's F16 ruling, final):** a hook has no terminal and may carry an agent marker, and the person-only gate on a network and git write is not weakened for one flag. The person who wants sync at the end of a session puts the command in their own shell, not in a hook amem registers. It does nothing without a configured remote (no `.git` is created), nothing when it is not due, and it stops a running git step after 30 seconds: git runs in its own process group for that call, so the stop reaches the transport children git started (ssh, a credential helper) and not git's pid alone. Because that group no longer receives what the terminal sends to amem, amem turns Ctrl-C (SIGINT), SIGTERM, SIGHUP (the terminal closed, which is also how an EXIT trap's shell goes away) and SIGQUIT into the stop (`on`, not `once`, so a second Ctrl-C is not the default action that would end amem before git), and a process that exits for any other reason signals every live git group first (an exit handler, installed when the first deadline git starts). Tested with the real binary under a pty for each of the four signals, three Ctrl-Cs in a row and a group SIGHUP, and with a process that dies by an uncaught throw. The one thing nobody can handle is SIGKILL of amem itself (or a power loss): the step timer dies with amem, so a git already running is left with nothing to stop it and runs until it finishes or its transport gives up. The next sync takes over `sync.lock` once amem's pid is gone and removes `index.lock`, which can then land under that live git. This is the existing hazard of any killed sync, and `--if-due` does not widen it; it is not closed here (`ponytail`: a group-aware stale-lock check in `sync.ts`, if a killed sync is ever seen to corrupt the index). The 30 seconds bound the git steps. It does not bound the `gh` visibility lookup (its own 15 s limit) or the cleanup `git merge --abort` after an interrupted merge, which deliberately ignore the stop so the repository is left clean (up to 60 s). After a success the next attempt is due an hour later; after a failure the wait is 15 minutes and doubles with each further failure up to a day. `--force` (only with `--if-due`) ignores the schedule and the backoff. The only state is `sync-state.json` beside the logs: two times and a failure count, never an error text (a git error can carry a remote URL), mode 0600, written by every `amem sync`, plain or scheduled. A damaged or hand-edited stamp, and one dated in the future, read as no history. Only a transport failure counts, and a run its person ended does not (`stopSignal().cause()` is `person` for Ctrl-C, SIGTERM, SIGHUP and SIGQUIT and `deadline` when the 30 seconds run out, whichever came first; a person's stop is classed `local` whatever step it hit, since the same Ctrl-C reads "fetch failed" or "stopped" depending on the step, while the deadline stays a failure because a remote that did not answer in time is worth backing off from): the real result is read (also under `--json`, which returns a failed sync instead of throwing), and a refusal no remote ever saw (another sync or mutation holds the lock, no remote is configured, the policy declines a note, the remote is public, a usage error) is not stamped, so it neither backs the schedule off nor makes a contended run look like a failed one. The read-modify-write of the stamp is not locked: two syncs finishing together can lose one count, which at worst delays a backoff by one step (`ponytail`: a lock if a scheduler ever runs several at once). Doctor reports the remote as `configured` or `none` (never the URL; read from the active profile's own repository: the shard cache of a split home, `generations/<G>/.git` of a generation home, `.git` of shared-v1), the last attempt and success, the failure count and the next attempt, and is `attention` when a remote has had no success for 7 days or has failed 3 times in a row.
- *Option A, rejected.* A detached bounded `amem sync` child started from the SessionEnd hook would hand network and git work to a hook. `AGENTS.md` forbids a model or network call on the capture path and a resident process, and `test/hooks-network.test.ts` runs the executable hooks, the SessionStart brief, native ingest and the capture append under network tripwires and observes no attempt, so a sync wired into them would have to change that contract. A detached child outlives the hook's own budget and cannot be accounted to it. The choice stays with the person: a hook is not asked to do it. `test/sync-cadence.test.ts` greps the setup, hook and ingest sources for any sync wiring and the cadence module for any process or timer.

## Agent proposals and person-reviewed lifecycle (F8, F9, AC4)

- `amem_remember` keeps its text form and optional explicit note kind. Its structured fail form requires `kind: fail`, approach, symptom, cause, evidenceRefs and retryWhen together, with no mixed text/title. `amem_correct` takes an exact visible entry id, proposedText, reason and optional decision/contract/fail kind. Both write only machine-local pending candidates. The host binds the project and target revision; model arguments cannot choose a home, project, actor or revision. Current configured policy screens the complete proposal and visible target before and after asynchronous checks. A stale, superseded, private or inaccessible target refuses without a curated append. MCP correction is restricted to the bound project, matching its show/search visibility; another project's shared entry also refuses generically. The complete accepted correction body, including provenance headers and reason, must fit the v1 4000-character limit already at proposal time.
- Person review accepts memory, correction, fail and promotion candidates in shared-v1, generation and split homes. Acceptance rechecks the current home, selector, aliases, realm, project lifecycle, exact target revision and policy. A split store writes to its bound shard and leaves legacy logs alone. Existing actor, current-policy and stale-target refusals remain. This replaces the earlier #15 split-home and generation CLI review deferrals; it does not add agent authority.
- A `promotion` candidate is a new machine-local candidates.db variant, not a correction or a shared-v1 operation. `goal done` (also `goal state <id> done`) records the person's goal state, then offers live linked short notes via the goal's recorded task links or `about: goal:<id>`. No live board is required. Offers are revision-bound and idempotent across pending, accepted and rejected states while their sidecar receipts are retained; repeated bounded runs advance through new offers. Existing candidate retention still applies, so a rejected note can be offered again after its receipt expires. Current goal, note and configured policy are rechecked after awaits. Unknown or withheld notes are never promoted implicitly. Person acceptance calls the existing `store.promote`, retaining its canonical id, original attribution and promotedFrom provenance. Earlier notes and shared-v1 hashes are unchanged. A host using rawGoalCommand without the optional onDone callback keeps its previous behavior.
- `amem decay [ids...] [--days N] [--json]` previews by default. The default is live, non-superseded long notes strictly older than 90 days. Open, active or blocked goals protect their linked tasks and goal/task about nodes. Any retained positive citation telemetry can only exempt otherwise eligible notes (the counter timestamp is the original delivery time, not a later citation update); missing, unreadable or zero observations never establish an absence of citations. The report labels citation history unknown, and an unavailable exemption count is null.
- `--apply` is person-only, with terminal input and a visible fresh revision preview before explicit confirmation. It acts on the named ids, or the displayed bounded set when none are named. Every selected exact revision, current policy, goal protection, citation exemption and profile binding is checked before the first effect. Default action is demotion to the short tier. The exact expiry is displayed before confirmation, written into every completed demotion and returned in the receipt; the default is 14 days, so reversal is available only until that expiry. A confirmation left open beyond the displayed deadline refuses before effects. Explicit deadlines must be canonical future UTC and no later than the store's configured short-tier TTL plus one hour from now; core demote and whole-batch preflight use the same validator. `--forget` must be supplied for each forget run and its confirmation explicitly names forgetting, that hidden claude-mem-imported copies need separate review; decay refuses expanded groups. There is no automatic deletion. The synchronous library apply additionally requires confirmed=true for bulk or forget; the CLI confirms even a named subset.
- Decay forget checks every actual forget group before confirmation and again during whole-batch preflight; any expansion beyond one exact reviewed id refuses. A core exact-only guard repeats this check immediately before its append. Thus an unseen, policy-withheld, stale or open-goal-protected imported copy is never removed by decay. Ordinary person `forget` keeps its existing legacy group operation after separate review. `ponytail:` decay does not yet offer a group-aware preview with per-copy revisions and policy/goal checks; that is the upgrade path for duplicate imported groups.
- `ponytail:` previews/offers cap selected notes at 64 and scans at 5000, but existing list/get still materialize the core corpus first; a scope-aware pager including shared rows is the upgrade. Exact-target checks use the existing sorted shard writer fences; older/raw writers that bypass them retain the mutation-lock ceiling. All selected checks precede all effects, but a later filesystem failure can leave an append-only partial batch. DecayApplyError carries applied (completed ids), failed (the uncertain target) and remaining (unattempted ids), plus the completed demotion expiry. CLI failure output prints them, or emits standalone JSON under --json (including failedMayHaveChanged: true), exits unsuccessfully and warns that the failed target may also have changed. There is no automatic retry. Goal state remains done if offering subsequently fails; rerunning done offers only missing candidates. A thrown promotion append keeps the existing accepting/manual-inspection recovery state, while a clean refusal returns the candidate to pending. Release compatibility: amem 0.6.0 and older CandidateStore.list() throws invalid candidate kind on a promotion row. Upgrade every reader/writer of this machine-local candidates.db before using goal-done promotion offers; the next package release must carry this compatibility note. This does not change curated shared-v1 rows.

Existing host person:false reads cannot gain history merely by forwarding new flags. Search selects matching historical versions; use show on a hit for its chain. Dates use UTC midnight for YYYY-MM-DD, or a canonical millisecond/Z timestamp; future times are refused. The CLI does not combine these modes with cross-project or repository-scope recall: those combinations refuse rather than mixing current rows into past state.
- Historical projection verifies retained originals with the existing legacy reader or generation source snapshots and reuses the same lifecycle reducer. It never rewrites authored rows, reconstructs physically pruned text or changes the v1 schema/hash/ops. Every current forget/prune mask applies at every requested date, including known promotion ancestry. A forgotten retained entry can produce only an id/time stub, never its old text. This privacy overlay means as-of is retained past state under current removals, not an archival recovery of deleted content. Malformed rows, incomplete tails and display limits are visible as incomplete results, including known generation skipped-row and committed-capture tail diagnostics. Diagnostics describe the opened retained inputs; unrouted malformed global pre-split rows are not reread or assigned a fabricated per-shard count. Current/history reads defer implicit promotions, and rebuild parity remains unchanged.
- `ponytail:` promotion retains the source's valid-at/provenance time and does not serialize its actual append time. Only actually emitted promoted rows make a historical result incomplete with exactly `promotion time unknown: tier before promotion cannot be recovered`. No timestamp is invented. The upgrade is a promotion timestamp in a future op version. Historical reads also fail closed above 50000 retained records or the 32 MiB verification-read/body budget; the row-data budget includes verification passes and is shared through generation refresh/rebuild and retries before reading, hashing or allocating new segment data. Scoped streaming history with durable proof checkpoints is the upgrade for larger homes.
- `(stale?)` is an advisory path hint: a referenced path is missing or its filesystem modification time is newer than the note's retained time. About paths resolve against the bound repository root even when called from a subdirectory. Missing paths without a confirmed root are unknown. One call probes at most 32 path components, never follows symlinks, and applies literal/folded denies, configured policy and an optional host lexical-private-path callback before access. Unreadable, denied or unprobeable paths are unknown and receive no marker. Current CLI --json retains the byte-compatible raw View shape; human output and intent-brief bodies carry the hint, while MCP and new historical output can add advisory metadata. No source contents or code structure are indexed. `ponytail:` this metadata hint cannot prove arbitrary content changes or concurrent hostile ancestor replacement; descriptor-relative traversal and an explicit host code-facts proof are the upgrade, not a stored code index.
- `amem brief --for <intent> [--paths <path>] [--symbols <symbol>] [--bytes N]` and `amem_brief` call buildIntentBrief. Paths/symbols are explicit, raw and normalized symbol forms remain queryable, directory scopes match whole path components, and graph expansion is one public co-reference step, not a transitive walk. Live fails come first, then decisions and contracts; findings are not included. Each call builds one immutable policy snapshot, screens eligible rows once and reads one source snapshot. Policy runs before relevance, bridges and output caps. Config and metadata-only source revision guards fence all intervening awaits; a change refuses the snapshot rather than publishing stale rows. A host PII gate remains checked across awaits; denied turns query nothing. Every adapter supplies a policyVersion guard (a constant is valid only for an immutable policy); mutable source adapters supply assertCurrent. The built-in source adapter is a call-scoped immutable snapshot with its own revision guard, so construct one for each brief call. Optional stale-probe failures remove only the marker, preserving screened memory.
- The complete brief body (untrusted-data header plus JSON lines) has a UTF-8 byte cap: default 2048, at most 8192. Individual excerpts are at most 768 bytes with a visible fetch/truncation marker, so an oversized first fail is not silently displaced by shorter decisions. Only emitted rows appear in the library result.items. CLI/MCP JSON envelopes expose the bounded body and small status metadata, never a second full copy of the item bodies. The exact-project source selects at most 5001 eligible-kind references before bodies and folds lifecycle metadata once; truncation is explicit. One bound snapshot supplies both output and a metadata/SQLite revision guard, with no body re-read. Invalid named paths cannot broaden into intent fallback; fallback omits stopwords. `ponytail:` lifecycle metadata still folds over the existing core; a measured derived validity index is the upgrade before increasing scan limits.
- planGuardNodes and matchingPlanFails are host-neutral exports: the host supplies screened live rows and its PII gate. The matcher uses explicit paths/symbols and no filesystem probes, and rejects superseded or explicitly expired fail rows. Finite future valid-at values remain visible in current recall for clock skew; the time cutoff is an as-of operation only. The AC6 library compatibility test passes a structural hub task/adapter to the same exported brief and plan functions. The agent-hub adoption/pin-bump/test half is agent-hub backlog card 436, blocked on this change and a separately authorized agent-mem release; no hub source changes ship here.
- F12 reuses machine-local candidates.db counters. recordMemoryUse and memoryUseCallbacks record explicit per-delivery totals, not implicit increments. Rendering means an entry is included in emitted output. CLI waits for a successful stdout write; MCP waits for its successful response write callback. Preparing a result, returning a handler value, a serialization/write failure or an error response records nothing. Delivery and citation require explicit host callbacks and are never inferred from output or a tool response. Opaque session/emission identifiers carry no note text. Automatic emission tracking is best-effort and bounded at 256 curated ids per output; unrecorded entries remain unknown, never zero.
- readMemoryUse leaves missing metrics null, including a total with any missing/invalid constituent, or numeric overflow. A known empty set has zero observed records and null metrics; an unavailable store has unknown record count too. Explicit zero is preserved. Repeated callbacks on the same delivery key are idempotent through the existing upsert. ## On-demand consolidation and evidence (F18/F19)

`amem consolidate [--project <current-key>]` is a person-only candidate writer, never a curated-memory writer. It screens one project-local snapshot under one guarded policy revision, then uses at most 256 verified-synced live rows and emits at most 32 deterministic proposals. FTS5 overlap plus shared paths suggests a merge; identical text suggests a replacement; a current head's retained supersession metadata gives chain context. FTS unavailability uses literal token overlap and is reported. A pair of related fail notes can propose a recurring-failure summary only when a related actual decision or contract is present. The proposal asks the person to assess that relationship and never invents a fix. An accepted consolidation note (first line `Accepted consolidation candidate:`) is never a source: it neither seeds a fail or recurring-fix proposal nor a chain summary, so repeated runs do not summarize their own summaries. `--project` must be the current project (the repository policy that narrows screening is the working directory's). The report counts only candidates newly queued or still pending as queued; proposals whose candidate was already accepted or rejected are counted as `alreadyReviewed`. Every quoted source is preserved whole; a proposal that cannot fit the candidate/note bounds is counted as oversized. Truncation is explicit.

Consolidation payloads live only in `candidates.db`, with the existing candidate hash/retention and person review flow. Curated shared-v1 schema, ops, hashes and paths do not change. A host with an older candidate reader must be upgraded before this payload is written into a shared home; older readers refuse an unknown candidate kind. Acceptance binds all exact source revisions, home/profile, project, placement and scope, and screens every source and the complete resulting note before appending. A stable host policy revision is required across all source verdicts and before effects. Transport placement comes from verified legacy segment locations (32 MiB read budget) or the generation index, never from tier or View.local. Unknown placement refuses the operation, local sources are excluded and counted, and local or mixed-placement acceptance refuses before any append. Merge and replacement acceptance supersede their sources; recurring-failure summaries keep their sources live. A rejected candidate remains rejected when the same proposal is generated again.

The v1 append log cannot make a multi-source replacement atomic. If supersession fails after the accepted note was appended, the candidate stays `accepting`; the error names the accepted note, confirmed supersessions and remaining or uncertain targets. Inspect those ids before any recovery. There is no automatic replay. The upgrade path is an explicit person-audited recovery protocol, not an unlogged retry. Proposal queue exhaustion likewise reports ids already queued and never changes curated notes.

`amem_evidence` accepts only a question, a limit (1..20) and a complete-JSON byte cap (256..8192, default 4096), under the MCP session's fixed project and home. It returns untrusted cited entries for the calling agent to reason about, never a generated answer. The existing curated FTS/BM25 and tier/recency ranking is used; capture, repo-only rows, pending candidates, foreign shared rows, invalid lifecycle rows and model-answer-marked rows never enter the evidence set or consume its final item cap. It makes no model call. Each packed citation is an exact `mem:<id>` and excerpts carry a fetch marker. Policy and source revisions fence asynchronous screening, and PII refuses before queries. The complete returned object, including question, header and provenance, fits the UTF-8 cap. A context that cannot fit is explicitly unknown rather than an answer with missing provenance. Only actually emitted entry ids may record rendered counters; a citation printed in this tool is not an observed delivery or citation event.


The optional consolidation model pass is a library-only injected callback, absent by default and explicitly enabled by the person. amem includes no provider or network client and never invokes it from capture or MCP. It batches at most eight screened, revision-bound, verified-synced sources, with complete input at most 8192 UTF-8 bytes, at most two batches per invocation and a 10-second abort deadline. Each output is at most 4096 bytes and must fit 3000 characters including its marker. A machine-local UTC-day reservation in `candidates.db` charges each attempt before invoking the callback, failures included: at most four attempts and 32768 input bytes per day, which also bounds maximum allowed output to 16384 bytes. Unknown budget state refuses; clock rollback cannot open a new allowance. No budget table is created on the capture or MCP read path.

A non-answer is never saved. Model output is stored only as a machine-local `model-answer` candidate with a `Model answer:` marker. Acceptance always refuses and points to `amem note add` for an independently authored note. It is never a curated entry, so evidence and briefs cannot consume it. A callback must cooperate with its AbortSignal to stop its own external work; an uncooperative host may keep working after the deadline, but its late output is ignored and cannot be saved. The upgrade path is provider-side cancellation/accounting in the host, not a built-in amem network client.
## Native-memory candidates and portable projects (F17, AC9)

- `amem import claude-auto [--from <projects-dir>]` reads only `*/memory/*.md` below the Claude projects directory. Without `--from`, it uses `$CLAUDE_CONFIG_DIR/projects` (else `~/.claude/projects`) and selects only the directory named by Claude's encoding of the bound repository's real path (`/` and `.` become `-`); an explicit `--from` selects all project directories below that root. `amem import codex [--from <memories-dir>]` reads bounded Markdown, text and JSONL records below `$CODEX_HOME/memories` (else `~/.codex/memories`). JSONL records are strings or objects with `text` and optional `title`. Both commands write only existing `memory` candidates for person review; they never write curated notes directly. Discovery and reads are bounded, directory iteration stops at 512 entries, source roots are canonicalized and every parent is checked before a read, and symlinks are not followed. Source-relative titles plus bounded text chunks make repeat imports idempotent. `CLAUDE.md`, `AGENTS.md`, `AGENTS.override.md`, `*.local.md` and `rules/` directories are excluded. Original source files are never changed. Tests use synthetic source roots only.
- Each complete external record has private spans stripped, then passes the configured standalone policy and built-in secret screen before it is split into chunks; each candidate retains the same checks. Records emptied by stripping are invalid. Empty or malformed records and policy/secret refusals are counted separately. One run adds at most 100 candidates; reaching that cap or a full queue returns a partial-count result with `limitReached` or `queueFull` instead of throwing. The result reuses `pendingSummary` to report the project's pending review count rather than adding another candidate reader.
- `amem project export <key> --to <file> [--format json|jsonl|markdown]` retains the #15 T5 project selection, lifecycle checks, privacy screen, exclusive 0600 destination and withheld counts. The default `json` bundle keeps the earlier structure. `jsonl` emits a header with the project's aliases, one typed record per capture row, authored curated note, goal and work list, then a counts record. Capture, goal and work-list rows stream; the current curated implementation materializes authored rows to preserve their identities. Authored rows, not derived views, preserve task expiry, demotion, reverse-supersession and alias identity. `markdown` presents the same selected rows as readable sections with metadata and bodies in indented code blocks; it is not a re-import format. Supersede, demote, settle and forget operations are not exported, so a fresh-home import restores authored note rows without replaying those lifecycle operations.
- `amem project import <key> --from <file.jsonl> [--confirm] [--allow-shared]` is person-only. Without `--confirm` it appends no curated notes and previews source, peer and scope counts plus the number of new ids; `--confirm` applies the same validation and writes. Shared-scope rows are invalid without the explicit `--allow-shared` flag. The header and project must match, and the target home must already have the exported aliases. Every row is validated before the first append: unknown fields, timestamps more than five minutes in the future, content changed by private-span stripping or length caps, and `supersedes`/`promotedFrom` targets outside the same file are refused. Current policy screens each stripped note. Entry ids are recomputed inside `importNote` and checked before any append, so a second import adds nothing; this proves self-consistency, not provenance. Capture rows, goals and work lists remain export-only in this version. Imports open one no-follow descriptor, verify a regular file, stream lines with a running 64 MiB cap and a 64 KiB line cap, and do not reopen a replaced path.
